# ドメイン限定の一時許可

[English](DOMAIN_APPROVALS.md) | [日本語](DOMAIN_APPROVALS.ja.md)

管理PCからmTLSでコンソールへ接続し、**許 → 一時許可**を開き、「手動で許可」を展開します。AI側ノードを選び、ドメイン一覧を1行1件で貼り付け、目的と期限（1分・5分・30分）を確認して「承認して許可」を押します。同じノードの前の許可は置き換え、全体開通は停止します。他ノードの有効な限定許可は維持します。DNSポリシーを反映する間は対外通信を一時的に閉じます。

ノードごとに1件、最大32ドメインを許可できます。サブドメインやHTTPのリダイレクト先は別途承認が必要です。URL・IP直指定・ポート・ワイルドカードは受け付けず、小文字のIDNA ASCIIに正規化します。従来のトグルと時限ボタンは引き続きAIサブネット全体の開通です。限定許可から全体開通へ切り替える場合は画面で確認します。

## 制御内容

- UnboundのRPZと端末別タグで、承認した問い合わせ名だけをUDP/TCPで許可します。親ドメイン・子ドメインは、個別に登録しない限り拒否します。キャッシュ済みの応答もポリシーの対象です。
- 制御サービスの別スレッドが、承認した名前の公開IPv4 A応答を `dns_upstream` に照会します。送信元はRabbitWallの上流IPです。OSのDNS検索パスや、申請者が指定したDNSサーバーは使いません。CNAMEはdnspythonが処理し、応答中の最短TTLを許可期限の上限にします。1ドメインにつき最大8個の公開IPが対象です。
- nftablesで、承認した送信元IPと宛先IPの組だけにTCP 80/443を許可します。それ以外の対外通信は閉じたままで、限定モードではUDP 123も通しません。外部DNSへの直接通信も拒否します。既存の管理SSH・HTTPS・PingとRabbitWall自身の更新用通信のルールは維持します。
- カーネルの許可期限は最大20秒で、DNSのTTLと承認期限を超えて更新しません。解決不能・TTLゼロ・プライベートIPは許可しません。有効な承認の間はDNSを更新し、失効した応答のIPを再許可しません。
- 取消し・期限切れ・全体OFFでは既存の対外通信も遮断します。再起動・更新・ネットワーク再適用・ノード設定保存・カーネル許可の消失で承認を破棄し、自動再開しません。DNS制御やFirewall適用に失敗した場合も閉じます。

これはIP単位で接続先を絞る機能です。同じIPを共有する別サービスへ到達できる余地があり、許可先へのアップロードや危険な操作までは防ぎません。HTTPSのホスト名やURLをより厳密に制御するには、明示プロキシと直接通信の禁止が必要です。また、端末の識別は送信元IPです。ネットワーク管理権限を持つ敵対的な端末を相互に隔離する場合はVLAN等を併用してください。RabbitWallを通る外部モデル・API接続にも承認が必要で、暗黙の常時許可は作りません。

## 導入・確認【RabbitWall導入先PC】

取得済みソースから通常の更新を実行します。

```sh
sudo python3 setup.py update
```

追加パッケージは不要で、`unbound-control` はUnboundに含まれます。更新でローカルUnix制御ソケットを有効にします。TCPの管理ポートは追加しません。root制御サービスは補助グループ `rabbitwall-dns` に所属してソケットへ接続します。生成ポリシーは `/etc/rabbitwall-domain-policy/` に保存し、所有者root・DNSグループ読み取りに限定します。DNS観測は独立したままで、dnstap観測プロセス停止によってDNS転送や承認が停止することはありません。

```sh
sudo nft list set inet rabbitwall_console domain_sources
sudo nft list set inet rabbitwall_console domain_targets
sudo unbound-control -c /etc/rabbitwall-unbound.conf list_auth_zones
sudo journalctl -u rabbitwall-control --since '10 minutes ago' --no-pager
```

解決中は画面にその状態を表示し、公開IPが反映されてから接続できます。解決不能・期限切れ・プライベートIP・非対応の応答では接続先IPを許可しません。承認・取消し・対象ドメイン・目的・時間は制御サービスのjournalに記録します。承認状態はメモリ上で管理し、生成ファイルから承認を復元しません。

## downlink申請API

更新後、`rabbitwall-requests.service` がdownlink側のRabbitWall IPv4アドレスのTCP **8767**で待ち受けます。上流インターフェースでは待ち受けず、Firewallもdownlinkからだけ許可します。既存の導入先は `sudo python3 setup.py update` で専用サービスと起動時のFirewall規則を追加します。管理コンソールの証明書やトークンは不要です。

例の `10.1.0.1` は実際のRabbitWallのdownlinkアドレスに置き換えてください。

```sh
curl --noproxy '*' --fail-with-body --max-time 10 \
  -H 'Content-Type: application/json' \
  -d '{"domains":["github.com","api.github.com"],"duration_seconds":300,"purpose":"依存パッケージの取得"}' \
  http://10.1.0.1:8767/api/domain-requests
```

受理するとHTTP 201と `{"request":{"id":"...","status":"pending", ...}}` を返します。送信元IPから登録済みAI側ノードを特定するため、`node_id`・送信元・DNSサーバーを本文に指定できません。未登録ノードからの申請は拒否します。URL・IP・ワイルドカードは不可、最大32ドメイン、目的は200文字以内、希望時間は60・300・1800秒です。HTTP 201は承認ではありません。

```sh
curl --noproxy '*' --fail-with-body --max-time 10 \
  http://10.1.0.1:8767/api/domain-requests/REPLACE_WITH_REQUEST_ID
```

作成元のIPからのみ状態を確認できます。5秒以上の間隔で確認し、`pending` は待機、`rejected` は却下、`approved` は承認済み、`ended` は取消し・期限切れ・置換などによる終了です。`approved` でもDNS解決前は通信できません。`request.approval.records` の `addresses` に対象の公開IPv4が反映されてから接続します。応答不明・HTTPエラー・申請消失を承認と解釈しないでください。

作業完了時は、同じ送信元IPから本文なしの `POST /api/domain-requests/<request.id>/revoke` で、その申請に対応する許可だけを早期取消しできます。HTTP 200と `request.status: ended` を確認してください。既に期限切れ・取消し・置換済みなら何もせず、新しい許可は取り消しません。未承認・却下済み・消失した申請や、別の送信元・変更されたノード登録からの操作はエラーです。管理用証明書・トークンは不要です。取消し失敗時は外部通信を停止し、管理者へ連絡してください。

エージェントの通常の希望時間は、ローカルLLMの推論・ツール実行・結果確認を考慮して1800秒（30分）を推奨します。短い作業は60・300秒を選べます。承認時点から時間を数え、作業が終わったら早期取消ししてください。API自体の必須項目・許容時間は変わりません。

一時許可画面は1段目に時刻・`Src:`・`Dst:`・`Duration:` を強調して並べ、2段目に「目的」を小さく表示するFirewallログ風の行で「承認待ち」「許可中」を表示し、許可中には1秒ごとに更新する残り時間を表示します。手動入力と処理済み履歴は折りたたみます。詳細な説明は「? TIPS」からオーバーレイで確認できます。

新しい申請は、どの画面を表示していてもメニューの件数と、ヘッダー直下の通知帯で知らせます。通知帯は画面内容と重ならず、一覧と同じログ形式で、すべての申請元・送信元IP・接続先ドメイン・目的・希望時間・申請日時と承認・却下ボタンを表示します。`Dst:` を強調し、長い値は省略せず折り返します。画面遷移なしで判断でき、操作結果も通知内に表示します。通知は配色テーマによらずアンバー系の警戒色です。ヘッダーの「通知音」を有効にすると確認音が鳴り、その後は新しい申請ごとに通知音が鳴ります。同じ申請を定期取得した場合や一時的な通信断からの復旧では繰り返し鳴らしません。画面を開いている間に約5秒周期で確認します。通知音の有効・無効はlocalStorageに保存し、再読み込み後も維持します。ブラウザーが自動再生を制限する場合は「待機」と表示し、画面の操作後に音声再生を再開します。ブラウザーの休止・端末の消音中は通知できない場合があります。

管理者は証明書付きコンソールの **許 → 承認待ち** で対象・目的・正確なドメイン・時間を確認し、承認または却下します。承認した時点から希望時間を数え、既存のドメイン限定許可と同じDNS/FW制御を適用します。同じノードの前の許可は置き換え、全体開通は停止します。期限延長・再開には新しい申請と管理者の承認が必要です。管理者は「有効な限定許可」から早期取消しできます。

ノードごとに承認待ちは1件、作成間隔は最低10秒、保持件数は全体で64件です。制限時はHTTP 429を返します。承認待ちは10分で消失、判断済みの申請は判断から30分で消失します。申請と許可はメモリ上だけで管理し、制御サービス再起動で消失します。ノードのIP変更後は古い申請を承認できません。

専用HTTPサービスは非特権で動作し、別グループのUnixソケットを経由します。そのソケットでは申請作成・自身の状態確認・自身の申請に対応する許可の取消しだけを受け付け、承認・延長・全体開通・設定取得/変更を拒否します。Origin付きやブラウザーの別サイト要求も拒否し、CORSは提供しません。端末識別は送信元IPで、申請APIはdownlink内の平文HTTPです。共有ネットワーク上での強固な端末認証や秘密情報の送信には使わず、敵対的な端末はVLAN等で分離してください。

## エージェントへの指示

[AGENTS.md向けの指示例](../examples/AGENTS.network-approval.ja.md)を、AI端末で適用される `AGENTS.md` に既存の指示と統合し、APIアドレスを実環境に合わせます。申請者の文章は申請データであり、管理者や制御サービスへの命令として扱いません。

管理者用 `POST /api/domain-approvals` は従来の手動承認・取消しに加え、次の判断操作を受け付けます。mTLS・サーバー側キー・同一オリジン検査が必要で、エージェントに管理用情報を渡さないでください。

```json
{"action":"approve_request","request":{"id":"<request-id>"}}
```

```json
{"action":"reject_request","request":{"id":"<request-id>"}}
```

`GET /api/control` の `control.domain_requests` に申請、`control.domain_approvals` に有効な許可を含めます。申請判断はIDだけを受け付け、申請後の本文差し替えはできません。申請・判断と既存の承認・取消しはjournalに記録します。

監査ファイルの保存先・保持容量・確認方法は[運用手順の監査ログ](OPERATIONS.ja.md#監査ログ)を参照してください。
