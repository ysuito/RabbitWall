2026-11-03時点。ローカルのソース精査と回帰テストに基づきます。導入先のOS・証明書・スイッチ・実際の経路を含む侵入試験ではありません。

## 今回の修正で対応した事項

- HTTPのヘッダー受信は合計5秒、本文受信は合計3秒に制限。少量ずつ送っても期限を延長しません。同時処理は全体32件・送信元IPごと8件に制限します。
- 初期導入・更新・ノード保存のFirewall設定生成を共通化。ノード保存後のFirewall再読込でも申請API用のTCP 8767の規則を保持します。
- Pythonテスト121件とJavaScript検証は通過。LinuxのFirewall再読込テストも追加しましたが、Docker停止中のため実通信での再実行は未完了です。

## 保留事項

### dnspythonのCPU枯渇によるサービス不能

**分類：既知脆弱性／対応保留。** [CVE-2026-114605の公式情報](https://github.com/rthalley/dnspython/security/advisories/GHSA-45c3-73f7-pv4m)では、上流の修正版は2.9.0です。

OSパッケージを優先する方針により、この件のためのpip・専用Python環境の導入、依存条件の引き上げ、新しい起動時検査は採用していません。既存の `dnspython>=2.6.1,<3` を維持します。導入先から報告されたパッケージは `python3-dnspython 2.7.0-1` です。OS側のバックポート状況は別途確認が必要です。

閉塞中のDNSパケットも観測用にPythonで解析するため、対外通信を閉じていてもパーサーへの入力は到達します。懸念はCPU消費による監視・観測の停止や遅延です。今回、この問題による任意コード実行やFirewallの許可回避を確認したわけではありません。

**再検討の契機：** OSの修正パッケージ提供時、監視プロセスの異常CPU使用が発生した時、AIセグメントに敵対的な端末を収容する時。バージョン番号だけでなく、ディストリビューションのセキュリティ更新情報を確認します。

根拠：`requirements.txt`、`src/rabbitwall/dependencies.py`、`src/rabbitwall/dns_drops.py`。

## 設計上の制約

| 懸念 | 条件・影響 | 対応を検討する条件・方向性 |
| --- | --- | --- |
| ドメイン限定許可はIP単位 | 最終的な許可は送信元IPv4・宛先IPv4・プロトコル・宛先ポートの組です。TLSのホスト名・HTTP Host・URLは検査しないため、同じIPを共有する別サービスへ接続できる余地があります。許可先を経由する転送やアップロードも制限しません。 | 正確なドメイン境界やアップロード制限が要件になった場合、直接通信を禁止したうえで、接続先を検証する明示プロキシ等を検討します。 |
| ノードの本人性は送信元IPに依存 | 同じAIセグメントでIP・ARP等を操作できる端末は、他ノードの申請元や通信許可になりすます余地があります。 | 敵対的な端末を混在させる場合、VLAN・スイッチ側の送信元検証等で通信経路と端末を分離します。申請APIに認証を加えるだけでは、IPで判定する通信許可の横取りは防げません。 |
| 申請APIは平文HTTP | downlink内の盗聴・通信改ざんに対する暗号化や端末資格情報がありません。管理用APIとは分離しており、申請者自身に承認権限は与えていません。 | downlinkの通信経路を信頼できない場合、HTTPSと申請専用の端末資格情報を検討します。管理証明書・管理トークンはエージェントに配布しません。 |
| DNS応答の信頼性が上流と経路に依存 | ローカルのDNSSEC検証と上流DNS通信の暗号化を有効にしていません。応答の改ざん耐性は、上流DNSとそこまでの経路に依存します。 | 名前解決の改ざん耐性が必要なら、DNSSEC検証や上流DNSへの保護された通信を検討し、RPZ・CNAME・閉塞時の挙動も合わせて検証します。 |
| 許可先への情報送信は防止しない | 全体開通時のHTTPSや、限定許可中の許可先へのアップロードは可能です。通信内容に基づく機密情報の持ち出し防止機能はありません。 | データ持ち出し防止が要件なら、接続許可以外にアプリケーション権限・秘密情報管理・送信内容の制御を設計します。 |

根拠：`src/rabbitwall/firewall.py`、`src/rabbitwall/request_api.py`、`src/rabbitwall/domain_requests.py`、`src/rabbitwall/unbound_config.py`。

## 追加の堅牢化と運用上の確認

| 項目 | 現状・残る確認 |
| --- | --- |
| 大量・分散リクエストへの耐性 | 受信期限と接続数上限は低速送信・接続占有を抑える対策です。複数送信元からの大量接続や高頻度の正規リクエストに対するサービス継続までは保証しません。必要な耐性を実測し、レート制限やネットワーク側の帯域制御を検討します。 |
| DNS観測とDNS本体の権限分離 | 観測プロセスとUnboundは同じユーザー／グループを使います。観測プロセス侵害時の影響範囲を小さくするには、アカウント・Unixソケット権限の分離が候補です。今回、その侵害につながる任意コード実行は確認していません。 |
| 履歴・申請目的・バックアップの機密性 | 通信先、申請目的、DNS履歴などが残ります。申請目的に秘密情報を入れず、ホスト・閲覧グループ・バックアップのアクセス範囲を管理します。 |
| 管理資格情報とOS更新 | 証明書・秘密鍵の保管、証明書失効や端末紛失時の手順、OS・Unbound・Caddy等の修正状況は導入先での運用確認が必要です。今回、実機の配置や更新状況は検証していません。 |
| RabbitWall以外の経路 | AI端末の別NIC・Wi-Fi・VPN等、RabbitWallを通らない経路はこのゲートで制御できません。複数経路がある場合は端末側も確認します。 |
| Linux実機の回帰確認 | Firewall再読込後の受付継続、systemdの起動順序、NIC・経路・閉塞の動作は実機またはLinuxの隔離環境で確認が必要です。 |

## 判断の前提

専用ゲートウェイと信頼する管理PCを前提に、明示的な管理者承認と時間制限で通信範囲を絞る設計です。上の制約は、新たな認証回避や任意コード実行を発見したという意味ではありません。敵対的な端末同士の隔離、厳密なドメイン境界、通信内容の検査まで求める場合は、追加の制御が必要です。
